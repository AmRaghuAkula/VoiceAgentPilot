> **For agentic workers:** REQUIRED SUB-SKILL: use superpowers:executing-plans (one task = one unit = one session). Steps use checkbox (`- [ ]`) syntax. [CLAUDE.md](../../../CLAUDE.md) §4–§6 is the authoritative lifecycle around every task; the steps below cover only the unit's own work.

**Goal:** build the calendar tool service described in the spec: an agent-agnostic, provider-agnostic HTTP service exposing `check_availability` and `book_appointment` to any agent that can call an OpenAPI (or MCP) tool, with Google Calendar as the first provider adapter, hosted as its own Azure Function, and verified by a live phone call through the production bridge (T6).

**Architecture (one paragraph; the spec is the source of truth):** a framework-free core (`calendar_tools/core/`: bindings, slot engine, slot tokens, identity HMACs, claim-store interface, booking algorithm) is wrapped by thin shells: an HTTP dispatcher with in-code Entra JWT auth (`calendar_tools/http/`), provider adapters (`calendar_tools/providers/`), the Azure Blob claim store (`calendar_tools/stores/`), a Key Vault secret source (`calendar_tools/secrets/`), and a one-function Azure Functions entry point (`function_app.py`). The telephony bridge (`server/`) is not touched and is not in the tool-call path.

**Tech stack:** Python 3.12, uv, `httpx` (async) for every outbound REST call (Google, Blob, Key Vault, JWKS), `azure-identity` (its async `azure.identity.aio` credentials, which need `aiohttp` as their transport) for managed-identity tokens, PyJWT + `cryptography` for token validation, `phonenumbers` for E.164, `PyYAML` for the OpenAPI document, `tzdata` (Windows has no system IANA database), `azure-functions` (imported only by `function_app.py`). Dev: pytest, pytest-asyncio, `respx`, `jsonschema`, `openapi-spec-validator`. IaC: Bicep + azd from `agent-tools/calendar/`, Entra app registration via `az ad`/`az rest`.

## 0. How to use this plan

- **The spec decides behavior; this plan decides files, order, tests and done-ness.** Every unit cites the spec sections it implements. Where a step says "per spec §7.4 step 6", implement exactly that text; do not re-derive it. Where the spec gives code (the §6.2 interface, the §4.1 binding example, the §5 JSON shapes, the §5.4 description strings), use it verbatim.
- **Where this plan had to reconcile the spec with reality**, it says so in §2 (P1–P18). Each reconciliation is recorded in D-056 (P18 was added during the UC00 PR's own code review, rev 1.4, while D-056 was still unmerged on the UC00 branch). None of them changes a spec decision (binding model, claim store, auth model, contract); they fill gaps or fix a contradiction the spec could not see.
- **If a unit finds the spec or this plan wrong** (an SDK or API behaves differently, a test cannot be written as stated), the builder stops and hands back to the partner (CLAUDE.md §5 step 4, §7). The partner revises the plan (and the spec if needed) before the unit resumes.

- **Serialization cost is accepted** (spec §14): UC units share the one-branch rule with bridge work. A live-call bridge fix may always be sequenced ahead of the next UC unit.

**Self-containment (spec §15.2)**
- Everything lives under `agent-tools/calendar/`: its own `pyproject.toml`, `uv.lock`, tests, `infra/`, `azure.yaml`, `.gitignore`. All paths below are relative to `agent-tools/calendar/` unless they start with `server/`, `docs/` or the repo root.
- It **never imports from `server/`**, and `server/` never imports from it. No shared config files. A test enforces the first half (UC02a, G1b).
- Nothing under `server/`, the root `infra/`, `hooks/` or the root `azure.yaml` changes in any UC unit.

**Content rules (CLAUDE.md §7/§9 as amended in UC00)**
- No real-estate words, agent names, project names, person names or real phone numbers anywhere under `agent-tools/`, tests included. The only exemption is `tests/genericity_denylist.txt` (G2). Test fixtures use: phone numbers in the NANP fictional range **exchange 555, lines 0100–0199, under a real area code** (e.g. `+1 613 555 0123`, written `+16135550123`; note spec §5.3's example `+1 555 010 0123` is malformed, P15), names such as `"Jordan Example"`/`"Sam Sample"`, binding IDs such as `test-alpha`/`test-beta`, appointment types `phone_call`/`in_person`, principal GUIDs generated with `uuid4()` or the fixed `00000000-0000-0000-0000-0000000000a1`-style constants.
- The real bindings file is never committed; `bindings.sample.json` holds fictional values only.
- **Evidence rule (public repo):** live-check artifacts (calendar screenshots, Foundry traces with transcripts, token dumps) stay **outside the repo** (the founder's own storage). STATUS.md, PR bodies and the email carry only redacted descriptions, `request_id`s, call `cid`s, and claim **names** (never `oid`/`tid`/principal values). Every test booking made in UC08b/UC10/UC12 uses a fictional contact.
- Never commit `.env`, `local.settings.json`, secrets, client JSON downloads, refresh tokens or keys. `agent-tools/calendar/.gitignore` (UC02a) lists them.

**Engineering rules**
- All commands run from `agent-tools/calendar/` and use `python -m uv …` (uv may not be on PATH).
- Every `git commit -m "…"` below is shorthand: append the `Co-Authored-By:` trailer of the model doing the work.
- Every external call is `async` and goes through `httpx.AsyncClient` with an explicit timeout (provider 3 s, claim store 1 s, Key Vault 3 s, JWKS 3 s) and is checked against the request `Deadline` (8 s) first (spec §7.5).
- Time and randomness are injected (`Clock`, `NonceSource`), never read from `datetime.now()`/`secrets` directly inside core logic, so every test is deterministic (P9).
- Logging: exactly one structured INFO line per request (spec §10) through `calendar_tools/obs.py`; nothing else logs contact data. `mask_phone()` keeps the last 4 digits only (`***0123`), the D-021 rule reimplemented locally (no import from `server/`).
- **Reason codes (spec rev 3.2 §10):** the OK outcomes are exactly health `ok`, `available`, `no_availability` and `booked` (replayed or not), logged with diagnostic `ok`, or an informational diagnostic where spec §7.4 names one (`claim_finalize_failed`, `duplicate_event_removed`, `stale_claim_recovered`; the first stays alerted). The guard applies only to non-OK outcomes. Every other outcome (every non-2xx included) logs a `diagnostic` that is neither empty nor `ok`, plus a `reason` from a closed, code-defined list wherever the diagnostic alone does not pinpoint the cause. For `invalid_request`, `invalid_slot`, `slot_unavailable` and `limit_reached` with no more specific §10 code, the diagnostic is the status name and the `reason` is `detail.reason` (or, for `invalid_request`, the comma-joined schema field names from `detail.fields`). A `reason` is never a value, token, contact field or vendor free text. Core exceptions carry their own `diagnostic` and optional `reason`, and the code that maps an exception to a status copies them into the log line instead of hard-coding a code. A required secret that is absent or fails its shape check is `secret_invalid`, never `secret_store_unreachable`. **Every code unit from UC03 on** asserts, for each non-OK path it adds, the logged `diagnostic` and `reason` (captured logs).

**Interfaces produced:**
- `http/app.py`: `Request(method, path, headers: Mapping[str,str] (case-insensitive), body: bytes)`, `Response(status, body: dict | None, headers)`, `CalendarService(config, bindings, authenticator, operations: Mapping[str, Operation], clock, nonce)` with `async def handle(req) -> Response`. `Operation` is `async (binding, body: dict, ctx: RequestContext) -> dict` where `RequestContext` carries `request_id`, `principal`, `deadline`, and the mutable `diagnostic` and `reason` that the operation sets (from the mapped exception's own fields, §1 "Reason codes") and the dispatcher's one log line reads.
- `http/auth.py`: `JwksCache(tenant_id, http, clock)` (fetch `https://login.microsoftonline.com/{tid}/discovery/v2.0/keys`, cache 24 h, refresh on unknown `kid` at most once per 5 minutes), `Authenticator.authenticate(auth_header) -> Principal` raising `Unauthorized`.

**Dispatcher rules (order matters; one test per rule and one for the order):**
1. `GET /api/health` → 200 `{"status":"ok"}`, no auth, nothing else in the body.
2. Path must match `/api/v1/bindings/{segment}/{op}` with `op` ∈ registered operations and `segment` a single non-empty path segment; otherwise 404 with an empty body. A segment that fails the binding-ID regex is **not** a 404: it is treated as an unknown binding and gets rule 6's identical 403 after authentication (spec §4.2).
3. Method must be POST (GET only for health); otherwise 405 with `Allow`.
4. Body larger than 8192 bytes (by `Content-Length` or actual length) → 413 `{"error":"payload_too_large"}`.
5. Missing/invalid token → 401 `{"error":"unauthorized"}` + `WWW-Authenticate: Bearer`.
6. Unknown (including syntactically invalid), disabled, or not-allowlisted binding → 403 `{"error":"forbidden"}`, **byte-identical** across all these cases.
7. Body not JSON, or JSON but not an object → 200 `{"status":"invalid_request","request_id":…,"detail":{"fields":["body"]}}`.
8. Unknown top-level request fields are dropped before the operation sees the body; their **names** are logged at DEBUG, never their values.
9. Every 2xx body carries `request_id` (a 16-byte hex nonce); the one `log_request` line is always emitted, including for 401/403/404/405/413 (with `binding_id` only if the path parsed). **Each refusal logs its own diagnostic and reason (spec rev 3.2 §10):** 404 `not_found`, 405 `method_not_allowed`, 413 `payload_too_large`, rule 7 `invalid_request`; 401 `unauthorized` with a `reason` naming the failed JWT check (`token_missing`, `token_malformed`, `alg_rejected`, `kid_unknown`, `signature_invalid`, `issuer_mismatch`, `audience_mismatch`, `tenant_mismatch`, `token_expired`, `token_not_yet_valid`, `role_missing`, `principal_claim_missing`), or, when the JWKS cannot be fetched, diagnostic `jwks_unreachable` (reason omitted); 403 `forbidden` with `reason` ∈ `binding_unknown`, `binding_disabled`, `principal_not_allowed` (the response body stays byte-identical, rule 6) and `principal` set from the token. A stub operation that sets no diagnostic on a non-OK result fails `log_request`'s guard.

**Interfaces produced:**
- `secrets.keyvault.KeyVaultSecretSource(http, vault_uri, token_provider, clock, ttl=300 s)`: `async get(name) -> str` (cached 5 min; a rotated version is picked up after TTL, spec §8.3 step 10), `async set(name, value) -> version_id` (used only by the consent tool). A 404 raises `SecretNotFound` (defined in `secrets/keyvault.py`), and the absence is cached for the same TTL, so an optional secret that doesn't exist costs one Key Vault round trip per 5 minutes, not one per request; every other failure → `SecretStoreUnavailable` (P3).
- `secrets.keyring.KeyVaultKeyRing(source: KeyVaultSecretSource)` implements UC03's `KeyRing` Protocol (P18): `async load(deadline) -> KeySet` reads `slot-token-key`, `slot-token-key-previous` and `fingerprint-key` (§3) concurrently through `source.get`, each under `asyncio.timeout(deadline.timeout_for(3 s))`, and base64-decodes each `str` value to `bytes`. `slot-token-key-previous` → `SecretNotFound` → `slot_previous = None`. A Key Vault failure or timeout on any read → `SecretStoreUnavailable` (diagnostic `secret_store_unreachable`). A required key that is missing, empty, not valid base64 or not 32 bytes → **`SecretInvalid(secret_name, check)`** (rev 1.6; diagnostic `secret_invalid`, reason e.g. `fingerprint-key.wrong_length`), never its value. It is a `SecretStoreUnavailable` subclass, so callers' mappings are unchanged, but the log line now tells "the vault is unreachable" from "the value we loaded is wrong" (spec rev 3.2 §10, F4; on the SMS track two secrets saved empty showed only as a reasonless `unavailable`). `DeadlineExceeded` from `timeout_for` propagates unchanged. Scopes: `https://www.googleapis.com/auth/calendar.freebusy` and `https://www.googleapis.com/auth/calendar.events.owned` (constants; UC08b may switch the second per spec §8.3).
