### Gaps found only by reading the app code and upstream comments, not the Bicep alone

These were missed in rev 1 because they only surface once you trace how the *deployed* configuration (system-assigned identity, no API key) interacts with code that already exists — both our own and unmodified upstream code.

- **C1 — the identity switch has a real circular-dependency problem, and it's not just the registry pull.** `main.bicep` line 80's own comment says the accelerator uses a **user-assigned** identity specifically *"to avoid circular dependency."* The reason: a system-assigned identity's principal ID does not exist until the Container App resource itself is created, but two separate things inside that same Container App's first deploy need an identity to already exist:
  1. **The registry pull** — `infra/modules/containerapp.bicep`'s `registries: [{ server: ..., identity: identityId }]` (lines 78–83), granted `AcrPull` by **`infra/modules/containerregistry.bicep`** (not `roleassignments.bicep` — this is a separate file, confirmed by reading it: its own `acrPullRole` resource at lines 39–47 grants `AcrPull` to `appIdentity.properties.principalId`, i.e. today's user-assigned identity specifically).
  2. **Key Vault secret references** — `containerapp.bicep`'s `secrets: [...]` block (lines 84 onward) sets an `identity:` field on each Key Vault-backed secret (e.g. line 89, `identity: identityId` on the ACS connection string secret). These are resolved by the platform **at the same revision-creation time** as the registry pull, not lazily at runtime — so a system-assigned identity granted Key Vault Secrets User *after* the Container App resource exists still fails to resolve its own secrets on the **first** deploy, for exactly the same chicken-and-egg reason as the registry pull. This half of the problem was missed in rev 2, which treated Key Vault access as something a post-creation role assignment could simply fix — it cannot, on a first deploy, without one of the two concrete approaches in U14b below.
  Switching to system-assigned without resequencing both of these creates a chicken-and-egg deployment failure on the **first** deploy (subsequent deploys, where the identity already exists, might appear to work, masking the problem until a fresh environment is provisioned). See U14b below for the actual resequencing design, and Q-015 (new) asking whether the founder wants to revisit Q-004 now that this cost is visible.
- **C2 — unmodified upstream `config_validator.py` will crash-loop the container under a system-assigned identity with no API key.** Read in full: `server/app/config_validator.py` lines 32–39 exits the process (`sys.exit(1)`) unless **either** `AZURE_VOICE_LIVE_API_KEY` **or** `AZURE_USER_ASSIGNED_IDENTITY_CLIENT_ID` is set. A system-assigned identity has no client ID env var of this kind (that variable name is specifically the *user-assigned* identity's client ID, which `containerapp.bicep` sets today at line 153 — removed by the identity switch). **Confirmed this file is unmodified upstream code**: `git diff upstream/main -- server/app/config_validator.py` returns empty. Per D-016, upstream code is out of review-fix scope by direct edit; the correct approach is a small hook, per D-002, with its own D-NNN — **do not** work around this by setting an API key, since that directly reopens Q-009 and violates D-004's Entra-ID-only intent for agent mode. This needs a new, small `server/` code unit (see U-CFG below), sequenced before U15's `azd up`, not a Bicep-only fix.
- **C3 — `ACS_COGNITIVE_SERVICES_ENDPOINT` is required by our own code and entirely unwired in Bicep, and (corrected in rev 3) the role assignment must go on the ACS resource's own identity, not the Container App's.** `bridge_config.py` (already merged, U04) already treats `ACS_COGNITIVE_SERVICES_ENDPOINT` as a hard startup requirement whenever ACS is active (line 141, raises `BridgeConfigError` if unset) — this is **not new code to write**, it already exists and already gates startup. But nothing in `infra/` sets this env var or grants the *right identity* access to the Cognitive Services resource for ACS's own text-to-speech calls (separate from the Voice Live agent connection). **Rev 2 got the role-assignment target wrong: it assigned Cognitive Services access to the Container App's own identity.** Per Microsoft's "Connect Azure Communication Services to Azure AI Foundry" documentation, the integration works the other way — **ACS itself calls the Cognitive Services resource directly** (for its own text-to-speech, independent of the Voice Live agent-mode connection the Container App makes), so the Cognitive Services User role must be granted to **the ACS resource's own system-assigned identity**, not the Container App's identity. Concretely, this needs:
  1. `infra/modules/acs.bicep` gets an `identity: { type: 'SystemAssigned' }` block added — it has **no identity block at all today** (confirmed by reading the file in full).
  2. The Cognitive Services User role assignment targets that ACS resource's own principal ID (`acs.identity.principalId`, available once the identity block above exists) on `hireastra-resource`, cross-subscription (same `scope:` mechanics as C5's Foundry User assignment, not the same role-assignment module that covers the Container App's identity).
  3. `hireastra-resource` must actually be a multi-service/`AIServices`-kind Cognitive Services account for this integration to work at all per Microsoft's own documentation prerequisite — confirm this against the portal at deploy time rather than assuming it, since `aiservices.bicep`'s own creation path already uses `kind: 'AIServices'` (line 48) for a freshly created resource, but `hireastra-resource` was created independently and its kind has not been independently confirmed here.
  4. U15's verification step must check **the ACS principal's** role assignment, not the Container App's — this was also wrong in rev 2's U15 text and is fixed there too.
  Two consequences if left unfixed: (a) the container may still crash-loop at startup for unrelated reasons (C2) even with this fixed, and (b) even past startup, ACS's own `play_media`/fallback-message calls would fail against a Cognitive Services endpoint its own identity has no role on — which directly undermines the Q-011 route-miss smoke test, since that test's whole observable signal is "the fallback message played" (`PlayCompleted`). Getting this role assignment wrong would make Q-011's own test fail with `PlayFailed`, not `PlayCompleted` — exactly the failure mode the test exists to catch, except caused by this plan's own Bicep rather than by the code under test.
- **C4 — `AGENT_ROUTING_JSON` needs a real (if placeholder) entry; it cannot be deployed empty.** `bridge_config.py`'s `parse_routing()` (line 73–74) requires a non-empty JSON object with a syntactically valid E.164 key — but there is no real number yet (Q-002 open). The plan must specify an actual placeholder value to deploy with, not leave this abstract. **Decision for this plan: use a fictional NANP number in the unused 555-01XX range** (e.g. `+15555550100`, matching the block IANA/NANPA reserve for fictional use in film/TV/documentation — never a real subscriber number), set via `azd env set AGENT_ROUTING_JSON '{"+15555550100": {"project": "hireastra", "agent": "re-intake-pilot-agent", "version": "10"}}'` at deploy time, **never committed to any file in the repo** (matches D-006/D-021's spirit of no real numbers in code, and this isn't a real number anyway). This value is replaced once Q-002 resolves and the real number is known (part of U16 or a follow-up).
- **C5 — cross-subscription topology (D-001) is unaddressed, including a real ambiguity in today's role-assignment module structure and a silent-failure risk in the postdeploy hook.** D-001 places ACS/`rg-hireastra-voice-pilot` in a *separate pay-as-you-go subscription*, while `hireastra-resource` stays in the *credits subscription* (`rg-hireastra`). U14a's "point at the existing AI resource" work is therefore a **cross-subscription** reference and role assignment, not a same-subscription one. Two concrete consequences, both belonging in U14a:
  1. **Role-assignment module scope is ambiguous today and needs an explicit fix, not just a "same pattern" note.** `roleassignments.bicep` currently declares its Key Vault and Cognitive Services role assignments as one module, implicitly scoped to wherever it's deployed (today, the same resource group as everything else, since everything lives in one subscription). Once the Cognitive Services/Foundry User roles target a resource in a **different** resource group and subscription (`hireastra-resource`/`rg-hireastra`) than the Key Vault role (which stays in `rg-hireastra-voice-pilot`), a single module can no longer cleanly cover both at once — Bicep resources referencing another subscription's existing resource need an explicit `scope: resourceGroup(subscriptionId, resourceGroupName)` reference, and role-assignment resources for that existing resource must themselves be deployed *at that resource group's scope*, not the deploying template's default scope. **The exact Bicep syntax for a role assignment against another subscription's existing resource's principal has not been independently verified while writing this plan** (this environment has no live Azure access to test it against) — this plan does not assert a specific, unverified syntax as fact; U14a's builder must get this exactly right during implementation (a `az deployment group what-if` dry run against the actual cross-subscription target, not just a same-subscription `azd provision --preview`, is the way to catch a scope mistake before a live apply) and should split `roleassignments.bicep`'s single module into (at minimum) a same-subscription module (Key Vault) and a cross-subscription one (Foundry User, and now the ACS-identity Cognitive Services User role from C3), rather than stretch one module across two scopes.
  2. **`hooks/providers/acs.postdeploy.ps1` uses the ambient `az` CLI's active subscription context, not `azd`'s own environment** — it calls bare `az resource list`/`az eventgrid event-subscription create` with no `az account set` of its own. Combined with `azure.yaml`'s `continueOnError: true` on the `postdeploy` hook (confirmed: line 33), **a wrong active `az` subscription at the moment `azd up` runs would make the Event Grid subscription step silently fail with no visible deploy error** — `azd up` would report success, but the Event Grid wiring the whole pipeline depends on would simply not exist. U15's own "Deploy" step must include an explicit `az account set --subscription <pay-as-you-go subscription id>` immediately before running `azd up`, not assumed to already be correct from a prior session.
  The deploying principal needs Owner or User Access Administrator **on the credits subscription** specifically (not just the pay-as-you-go one) to create the Foundry User/Cognitive Services User role assignments there. `AZURE_SUBSCRIPTION_ID` (the pay-as-you-go one, where `azd` provisions) must be pinned explicitly in the `azd` environment. This is foundational sequencing, not a nice-to-have, and belongs in U14a (the module-split design) and U15 (the `az account set` step).
- **C6 — the resource group and ACS resource may already exist, and accepting `azd`'s default naming could create duplicates.** Q-003's own answer implies the region for `hireastra-resource`/`rg-hireastra-voice-pilot` was already confirmed — plausibly because Cowork already created (or partially created) `rg-hireastra-voice-pilot` and/or the ACS resource itself while working the Q-002 ticket. If either already exists, accepting `azd`'s default `rg-<env>-<hash>` naming (rev 1's "pragmatic default" for Q-012) would silently create a **second**, different resource group, and a Bicep-created ACS resource (`modules/acs.bicep`'s unconditional `resource acs = {...}` block) would create a **second** ACS resource that the already-configured Event Grid subscription (if Cowork already made one) would not be watching. **Before U14a's design is finalized, Cowork must inventory what already exists**: `az group show --name rg-hireastra-voice-pilot`, `az resource list --resource-group rg-hireastra-voice-pilot -o table` (or equivalent in the pay-as-you-go subscription). If a resource group and/or ACS resource already exist, U14a's Bicep must reference them as `existing`, the same way it's being changed to reference `hireastra-resource` as existing — this is the same class of fix, just possibly needed twice. See Q-012 (revised) and Q-016 (new).
- **C7 — U15's smoke test needs the rest of the Step 3 bridge, not just U14's infra.** Rev 1 gated U15 only on "U14 merged." But the Q-011 route-miss smoke test's actual code path (`BridgeCallController.handle_incoming`/`_answer`, `called_number_from_event`, the signed callback/media URLs) lives in **U10–U12** (M4, not yet merged as of this writing — U10 is `NEXT` in STATUS.md §1), and the "complete bridge" milestone is U13 (M5). Deploying before U10–U13 merge would only exercise the **unmodified upstream** `event_handler.py`/`AcsEventHandler` (already read in full — it has no routing, no signed URLs, no `CallSession` lifecycle), which proves nothing about *our* code. U15's prerequisites are corrected below to require U10–U13 all `CLOSED`.
- **C8 — monitoring needs a Python code change, not just a Bicep parameter fix.** See the table above; restated here because it changes U14's scope, not just its DoD wording. Wiring `appInsightsConnectionString` through to the container's env array is necessary but not sufficient — without an Application Insights/OpenTelemetry SDK dependency in `server/pyproject.toml` and the corresponding SDK initialization in `server.py`/`server/app/`, no telemetry would ever reach App Insights regardless of how correctly the connection string is threaded through Bicep. This needs founder/partner sign-off on scope before U14a starts (see Q-014, rewritten) — it may be its own small unit, or the M6 DoD's monitoring bullet may be explicitly rescoped to "Log Analytics only for now, App Insights code instrumentation deferred," but that's a decision, not a default.
- **C9 — Key Vault's RBAC-only authorization means `az keyvault secret list` needs its own permission, separate from subscription Owner.** `keyvault.bicep` sets `enableRbacAuthorization: true` (no access policies) — verifying secrets exist via `az keyvault secret list` requires the *deploying/verifying* principal to hold a data-plane role (e.g. Key Vault Reader, or Key Vault Secrets User to read values) on the vault, which subscription-level Owner does not automatically grant. U15's verification step is corrected to either (a) confirm the founder's/builder's principal has this role first, or (b) verify via the Container App's own `secrets[].keyVaultUrl` list (a control-plane read, which Owner does cover) instead of listing the vault's secrets directly.
- **C10 — tooling prerequisites beyond `az`/`azd` are unconfirmed on the deploy machine.** Confirmed present: `az` CLI 2.90.0. **Not confirmed:** `azd` itself, `pwsh` (the hooks are written in PowerShell and `azure.yaml` runs them with `shell: pwsh`), and the `communication` `az` CLI extension (needed for `az communication identity user create`/`token issue` in the Q-011 smoke test — confirmed today it is **not installed**, and installing it via `az communication ...` triggers an interactive "install this extension?" prompt that fails non-interactively with `EOFError: EOF when reading a line` in this environment). U15's (and the Q-011 test's) prerequisites now include explicitly installing this extension ahead of time with `az extension add --name communication -y` (the `-y` flag bypasses the interactive prompt) rather than assuming it installs itself on first use.
- **C11 — cost flag for the founder, not a fix, but worth stating plainly before `azd up` runs.** Rough estimate at today's Bicep defaults: the Container App at 2 vCPU/4 GiB with `minReplicas: 1` (always-on) is commonly in the $45–55/month range on Consumption-based Container Apps pricing even fully idle; Azure Container Registry Standard tier is roughly $20/month; Log Analytics ingestion adds more on top of that. Combined, this plausibly **exceeds the spec's own suggested $50/month budget alert before any real call traffic**. This plan recommends right-sizing to something like 0.5 vCPU/1 GiB (`containerapp.bicep`'s `resources: { cpu: json('2.0'), memory: '4.0Gi' }` today) and ACR Basic tier instead of Standard, as part of U14c, but this is ultimately the founder's cost-vs-headroom call — flagged explicitly, not silently decided by the builder.

**Also verified (accurate, kept from rev 1 with corrections applied):** `hooks/preprovision.ps1` **does** prompt interactively (`Read-Host "Select provider [1]"`) whenever no telephony provider's credentials are already detected in the `azd` environment (lines 151–166) — pressing Enter at that prompt defaults to ACS with no further input needed, but it is still a real prompt, not a silent pass-through (**correcting rev 1's claim that it "branches cleanly... with no prompts"**). Pre-setting `TELEPHONY_PROVIDER=acs` via `azd env set` before running `azd up` does not itself suppress this prompt, because the script's branch condition checks whether *credential* env vars (`TWILIO_AUTH_TOKEN`, `INFOBIP_API_KEY`, etc.) are set, not `TELEPHONY_PROVIDER` directly (lines 140–150). Since none of those other providers' credentials will be set in this deploy, the founder/builder should expect this one prompt and simply press Enter — there is no way to pre-set a bypass for it today, so this is a known, accepted prompt, not a script bug to fix. Separately, `hooks/providers/acs.postdeploy.ps1` **has no interactive prompts at all** (**correcting rev 1's opposite claim** — it only reads `azd env get-value` and calls `az eventgrid` commands, with no `Read-Host` anywhere in the file), **but it does depend on the ambient `az` CLI's active subscription context, not `azd`'s own environment** (it calls bare `az resource list`/`az eventgrid event-subscription create`, never `az account set` itself) — see C5 below for why this matters and what to do about it. The model-selection prompt in `preprovision.ps1` (lines 37–107) is separately skippable by pre-setting `AZURE_VOICE_LIVE_MODEL=gpt-4o-mini`.

## Units

M6 follows the same discipline as M0–M5: **one unit = one branch = one PR**, founder "go" before the builder starts, Opus review (+ `cso` where there's a security surface) before merge, STATUS.md updated inside the PR. Because this is infra work rather than TDD-on-Python, "tests" for these units are **verification commands and their expected output** (`az` queries, `azd` exit codes, log greps), not pytest — except U-CFG, which touches `server/` Python and gets a real pytest-based unit test like every other code unit.

**Rev 2 splits rev 1's single oversized U14 into four smaller units** (U14a–d) plus a new small code unit (U-CFG), so each is independently reviewable and no single PR bundles "cross-subscription existing-resource wiring" with "identity architecture redesign" with "container sizing." ### U14a — Point at the existing `hireastra-resource` (cross-subscription), wire ACS text-to-speech, fix Container App scale

**Branch:** `feat/tb-m6-u14a-existing-ai-resource` · **Model:** Sonnet (mechanical parameter/reference wiring, no architectural ambiguity once C5/C6's topology is confirmed by Cowork first).

**Prerequisite:** Cowork has inventoried the pay-as-you-go subscription per C6 and confirmed (a) whether `rg-hireastra-voice-pilot` and/or the ACS resource already exist, and (b) the exact subscription ID, resource group name, and `hireastra-resource` region/name/resource-group-name pairing to reference. This is a Cowork/founder task, not something the builder guesses at — **do not cut this branch until that inventory is back.**

**What it does:**

1. **Existing AI resource, cross-subscription (C5).** Add parameters to `infra/main.bicep`: `existingAiServicesSubscriptionId`, `existingAiServicesResourceGroup`, `existingAiServicesName`. Reference it with an explicit cross-subscription scope (`resource existingAiServices 'Microsoft.CognitiveServices/accounts@2025-06-01' existing = { scope: resourceGroup(existingAiServicesSubscriptionId, existingAiServicesResourceGroup) name: existingAiServicesName }`), replacing the unconditional `module aiServices 'modules/aiservices.bicep' = {...}` call with a conditional (mirroring the existing `acs` module's `if (telephonyProvider == 'acs')` pattern at line 128) so the create-path stays available for any future environment that doesn't have an existing resource to point at. ### U14b — Resequence to system-assigned identity (the circular-dependency fix)

**Branch:** `feat/tb-m6-u14b-system-identity` · **Model: Opus** (per D-014 — this is exactly the "architectural, subtly wrong if done casually" work the founder should be asked about before the builder starts, given C1's finding; do not let this run on Sonnet silently).

**Prerequisite:** U14a merged.

**What it does:** resolves C1 — **both halves of it, corrected in rev 3.** Rev 2's Option 2 ("hybrid identity: user-assigned only for registry pull, system-assigned for everything else including Key Vault") **does not actually work as written** — Container App Key Vault secret references (`secrets[].keyVaultUrl` + their own `identity:` field) are resolved at the same revision-creation time as the registry pull, so a system-assigned identity granted Key Vault Secrets User only *after* the Container App resource exists still fails to resolve `ACS_CONNECTION_STRING`/`MEDIA_WS_TOKEN` on the **first** deploy, for the same chicken-and-egg reason as the registry pull. Say this plainly rather than presenting Option 2 as already working: **either Key Vault access stays on the user-assigned identity too (a genuine, larger hybrid than rev 2 described), or secrets get attached to the Container App in an explicit second deploy pass, the same way role assignments would be in Option 1.** The builder proposes one concrete approach and gets it Opus-reviewed before implementing, rather than the plan mandating a single approach up front, since this is exactly the kind of design call D-014 flags for extra scrutiny:

- **Option 1 — two-phase deploy.** First `azd provision` pass creates the Container App with a placeholder/no registry-pull identity (or a minimal bootstrap identity) and no Key Vault secret references, and captures its system-assigned principal ID as an output; role assignments (Key Vault Secrets User, Foundry User, the ACS-identity Cognitive Services User role from C3) are applied in a second Bicep/`az` pass once that principal ID is known; a further pass adds the Key Vault secret references to the Container App's revision once Key Vault Secrets User is actually granted; a final `azd deploy` pushes the real container image. This mirrors patterns Microsoft's own Container Apps + system-assigned-identity samples use elsewhere, and is more multi-step than rev 2's description implied once the Key Vault half is accounted for.
- **Option 2 — hybrid identity, corrected.** Keep a minimal user-assigned identity for **both** the registry-pull reference **and** the Key Vault secret references (the two genuine chicken-and-egg dependencies `containerapp.bicep` has today), and use system-assigned only for role assignments that are applied *after* the app exists and aren't needed to resolve the Container App's own revision at creation time (Foundry User, the ACS-identity Cognitive Services User role — note the latter is on the ACS resource's identity per C3, not the Container App's, so it's unaffected by this choice either way). This is a narrower "system-assigned for some things" outcome than rev 2 implied, and should be presented to the founder exactly this plainly — not as "system-assigned except for one small registry-pull exception" but as "system-assigned for the roles that can tolerate being granted after the app exists; user-assigned for anything the app's own first-deploy revision needs to resolve at creation time" (see Q-015, new, for the founder's explicit sign-off on this reframing of Q-004's answer).

Whichever option, `roleassignments.bicep`'s role-assignment resources move to depend on the Container App's own identity output rather than the other way around (today `containerapp` `dependsOn: [RoleAssignments]`; this flips for the system-assigned principal, at least for the roles that use it).

**A scratch/test environment used to validate either option costs real money and needs explicit teardown, and `keyvault.bicep` complicates a repeat attempt.** `keyvault.bicep` sets `enablePurgeProtection: true` (confirmed, line 34) — with purge protection on, a deleted Key Vault does not become purgeable early by anyone, regardless of role or permission: **the vault name stays reserved in a soft-deleted state for its full retention period (up to 90 days) and cannot be purged by any principal, no matter how privileged, until that period elapses.** This is a property of the vault's own configuration, not a permissions gap to route around. `azd down` (even with `--purge`) removes the billed resources it can delete, but a purge-protected Key Vault simply cannot be hard-deleted early — `azd down --purge` will still leave it soft-deleted. Practically, this means: (a) each repeat clean-environment test needs a **new** `environmentName` (not the same one reused), since the Key Vault name is derived from it, and (b) the scratch stack itself (Container App, Key Vault, Log Analytics, etc.) is real, billed infrastructure that needs its own explicit teardown once validation is done, not left running, while accepting that the Key Vault name itself stays unavailable for reuse until its retention period passes regardless of teardown effort. State this to the founder before running a validation pass, not discovered afterward as an unexpected charge or a name collision on a second attempt.

## Q-011 — Can a VoIP-only ACS call validate the pipeline before the number arrives?

**Conclusion (confirmed sound on review, with corrections to the test procedure below): yes, partially — it validates the wiring, not the agent connection, and only once U10–U13 and the C2/C3/C4 fixes above are all in place.**

### The evidence (read from the actual code, not assumed from the spec)

1. **`hooks/providers/acs.postdeploy.ps1`** creates the Event Grid subscription with `--included-event-types "Microsoft.Communication.IncomingCall"` and no number filter (until U16). ACS's `IncomingCall` event fires for any call reaching the ACS resource — by phone number or by a VoIP/ACS-user identity — and the subscription delivers both identically to `/acs/incomingcall`.
2. **`server/app/routing.py`'s `called_number_from_event()`** (already merged, U03) extracts the called identifier generically. In paraphrase, not as a literal code quote (**correcting rev 1**, whose quoted snippet did not match the actual function, which type-checks each step rather than chaining bare dict `.get()` calls the way the quote implied): it reads `data.get("to")`, and if that identifier's `phoneNumber` field is present and itself a mapping with a string `value`, returns that value; otherwise it falls back to the identifier's own `rawId` if present. A VoIP call's `to` field has `kind: "communicationUser"` with only a `rawId` (e.g. `8:acs:resource_user-id`), no `phoneNumber` — so `called_number_from_event` returns that `rawId`, which `resolve_route()` then fails to match against any real E.164 routing key. This exact scenario is one of the plan's own test cases (`test_resolve_miss` asserts a `rawId`-only identifier misses; the Task 8 plan text names it explicitly: *"A called number that isn't a phone number... The caller should hear the fallback message (a route miss), with no crash."*).
3. **`BridgeCallController.handle_incoming()`/`_answer()`** (Task 8, U10 — not yet merged as of this writing, but its code and tests are fully written out in the implementation plan) does not reject or special-case a non-phone-number `to` — it resolves a route-miss, still answers the call, still creates a `CallSession`, still logs `incoming_call route=miss`, and (per the M3 `CallSession` design) plays the fallback message and hangs up cleanly. A route-miss never sets `media_streaming` options, so Voice Live is never contacted — this is the one thing the test cannot validate, by design, not by accident.

### What this does and does not prove

**Does prove, end-to-end, once U15 is deployed with U10–U13 merged and C3/C4 fixed:**
- Event Grid → Container App wiring is live and correctly addressed.
- The Container App parses a real, live `IncomingCall` event shape (not a unit test's synthetic dict).
- `answer_call` succeeds against the live ACS resource with a real `incomingCallContext`.
- The route-miss/fallback-message/clean-hangup path works against live infrastructure — **specifically requiring a `PlayCompleted` callback, not `PlayFailed`** (**correcting rev 1**, which accepted either as a pass; a `PlayFailed` result would silently mean the TTS role from C3 is broken while still reading as "the pipeline responded," which is exactly the false-positive the review flagged).
- Bridge logs correctly mask/record the call (D-021) even for a non-phone-number caller identity.

**Does not and cannot prove:**
- Anything about Voice Live/Foundry agent connectivity — a route-miss never attempts it.
- Anything requiring a route **hit** (acceptance tests 1–6, 8) — these need the real number or a deliberate, founder-approved, separate scoping decision this plan does not make.

### Exact steps to place and observe a VoIP-only test call (staged by the builder/Cowork; placed/confirmed by the founder — see "who runs the smoke test" above, corrected in rev 3 to match HANDOFF.md's actual text rather than rewrite it)

1. **Confirm tooling first (C10):** `az extension add --name communication -y` if not already installed (do this ahead of time — the interactive prompt otherwise fails non-interactively).
2. **Provision two test ACS user identities** (not one — **correcting rev 1**, which provisioned one identity but the calling-SDK path in the next step needs both a caller and a callee identity to place a user-to-user VoIP call): `az communication identity user create --connection-string $env:ACS_CONNECTION_STRING` run twice. **Pass the connection string via an environment variable, never inline on the command line** (shell history exposure — a real, if modest, secret-handling concern the review correctly flagged). **How the operator gets the connection string onto their machine in the first place:** it lives in Key Vault (`ACS-CONNECTION-STRING`, wired in U14a), which needs the same data-plane role from C9 to read directly (`az keyvault secret show`) — if the verifying/testing principal doesn't already have that role from U15's own verification needs, request it explicitly rather than assume it's implied by subscription Owner.
3. **Issue a VoIP access token for the caller identity.** Confirm the exact flag name against `az communication identity token issue -h` at execution time rather than assuming `--user` (the CLI extension isn't installed in this environment as of this writing, so the flag name was **not** independently verified while writing this plan — this is flagged, not guessed). Check whether the extension offers an environment-variable-backed connection-string option (rather than a command-line flag) via that same `-h` output, and prefer it if available, for the same shell-history reason as step 2.
4. **Place the call using the ACS Calling SDK for JavaScript**, in a throwaway static HTML page (Microsoft's own quickstart pattern), targeting the second test identity as the callee. This triggers `Microsoft.Communication.IncomingCall` against the ACS resource the Event Grid subscription watches. **The Call Automation `create_call` alternative path rev 1 also offered is dropped from this plan as the primary recommendation** — the review correctly noted it is outbound calling (TELEPHONY_BRIDGE_SPEC.md §7's "Do not build... Outbound calling" list item), needs explicit founder sign-off even for a throwaway test script, needs a `callback_url` parameter rev 1's sketch omitted, and — most importantly — **whether an app-originated `create_call` to an ACS user even raises `IncomingCall` the way this test needs is plausible but was not independently verified while writing this plan.** If a future session wants to use this path instead of the Calling SDK, it must first verify that assumption against Microsoft's own docs or a scratch test, and must get the founder's explicit sign-off for the outbound-calling aspect, before relying on it.
5. **Watch the bridge's own logs in real time** (`az containerapp logs show --follow` or the Log Analytics workspace query) for `incoming_call route=miss`, followed by `PlayCompleted` (not `PlayFailed` — see the correction above) and `CallDisconnected`.
6. **Confirm in the Azure portal** (Cowork): the Event Grid subscription's delivered-event count incremented by exactly one for this test.
7. **Report the outcome** as part of U15's PR and the session's status update — pass/fail against the exact expected log lines, with the actual log line pasted (secret-redacted) as evidence.

**This test's own future is limited once U16 lands (cross-reference with Q-013).** Once the real ACS number exists and U16 adds a number-based advanced filter to the Event Grid subscription, that filter will also block this VoIP-only test's future delivery (a VoIP call's `to` has no `PhoneNumber.Value` to match) — so this exact procedure is only reusable **before** U16 applies its filter, or against a second, deliberately unfiltered subscription kept for test purposes if the founder wants to keep re-running it after U16.
