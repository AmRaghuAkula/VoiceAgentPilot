### D-020 · 2026-09-25 · pytest runs with `--import-mode=importlib`; shared test helpers live in `tests/helpers.py`, not `conftest.py`

### D-022 · 2026-09-25 · E.164 validation requires real NANP shape; unmatchable input is never coerced into a plausible number
`app.routing.is_valid_e164()` requires a NANP (`+1`) number to have real area-code and exchange-code shape (`+1[2-9]XX[2-9]XXXXXX`), not just "+1 followed by 10 digits". `normalize_number()` only reformats text that is already number-shaped (digits, spaces, `()`, `-`, `.`, optional leading `+`); anything else (an extension suffix, a GUID-derived ACS `rawId`, non-ASCII digit lookalikes) is returned unchanged so it can never accidentally match a routing table key. Both E.164 patterns are ASCII-only and fully anchored (`\A...\Z`), so a trailing newline or a non-ASCII digit lookalike cannot pass.
**Why:** the first cut of the NANP regex (`^\+1\d{10}$`) accepted a dropped-digit key such as `"1416555123"` (normalizes to `+11416555123`) as valid. Since `bridge_config`'s startup validator (U04) uses `is_valid_e164` to reject typo'd routing keys per design spec §3.1, a loose regex would have let a broken key start up silently — exactly the "route_miss on every real call, no error at startup" failure mode the design spec's own reviews warned about for the routing table. **Source:** U03's Opus code review, round 1 (found the gap and the over-eager normalization) and round 2 (confirmed the fix, found no regressions on real formatted numbers).

### D-023 · 2026-09-25 · Startup config validation: strict numeric parsing, per-field ceilings, and "fail loud, never fail quiet"
`app.bridge_config.load_bridge_config()` is the single startup gate for every ACS-related setting. It holds these properties, each added after an Opus review found a way to violate it:
- **Agent version pinning is ASCII-digit-only and rejects leading zeros/zero** (`\A[1-9][0-9]*\Z`), not just "any digit string" — non-ASCII digit lookalikes, `"0"` and `"007"` are rejected.
- **`_get()` strips whitespace and treats a whitespace-only value as unset**, so a blank secret, a blank endpoint, or a blank spec-name env var can never silently pass validation or silently win a precedence check (D-003) over a valid fallback.
- **Every numeric field** (`MAX_CALL_SECONDS`/`MAX_CALL_DURATION`, and all three connect/grace timeouts) is matched against an ASCII-only `\A[0-9]+(\.[0-9]+)?\Z` pattern *before* casting, so `inf`, `nan`, non-ASCII digits, underscores and scientific notation are all rejected outright, never silently coerced. Each field has its own sane ceiling: `MAX_CALL_SECONDS_CEILING = 3600` (matching the upstream accelerator's own default) for the call-duration field, `MAX_CONNECT_TIMEOUT_CEILING = 60` for the three short connect/grace timeouts (per design spec §3.1's 8–10s defaults).
- **`interim_response` is deep-frozen** (nested dicts → `MappingProxyType`, nested lists → `tuple`) and rejects `NaN`/`Infinity`/`-Infinity`, both as literal JSON constants and as float literals that would overflow to `inf` (e.g. `1e999`).
- **A duplicate JSON key is always caught and always names its source variable** (`AGENT_ROUTING_JSON has a duplicate JSON key '***1234'` / `INTERIM_RESPONSE_JSON has a duplicate JSON key 'a'`), and is masked whenever the key contains any digit (matching `mask_number`'s own "***" fallback for anything under 4 digits) — never only when the key happens to pass strict E.164 validation, since a duplicate typo'd or extension-suffixed number is exactly the case that must not leak (D-021).
- **Every parsing path that can raise `RecursionError` or a non-`BridgeConfigError` `ValueError` (e.g. Python's integer-string-conversion digit limit, currently 4300 digits) is caught and re-raised as `BridgeConfigError`.** `BridgeConfigError` itself is always re-raised before any broader catch, so it is never double-wrapped.

**Why:** this file is the sole thing standing between a misconfigured routing table and that misconfiguration silently reaching "production" — a typo'd number, an unpinned version, or a malformed setting must fail loudly at startup, never pass validation and only break on a real call. Four Opus review rounds on this unit found, in order: (1) fail-quiet gaps — non-ASCII version strings, whitespace-padded secrets, `inf`/`nan` timeouts, D-003 precedence broken by whitespace, uncaught exceptions; (2) a masking regression introduced by round 1's own fix, plus an `OverflowError` on huge integers; (3) the masking fix still missed non-consecutive-digit keys, a `_deep_freeze` recursion boundary outside the try block, `1e999`-style float overflow, and an ungrounded shared numeric ceiling; (4) round 3's exception-catch narrowing (removing `ValueError` from a catch clause) reintroduced the exact class of uncaught-exception bug round 1 had fixed. **Source:** U04's four Opus code review rounds, all run as separate subagents dispatched with `model: "opus"` from this session (which ran on Sonnet throughout) per CLAUDE.md §5.

### D-026 · 2026-09-26 · Agent-mode `interim_response` must be deep-thawed before it reaches Voice Live
`VoiceLiveMediaHandler._agent_session_config()` (`app/handler/voicelive_media_handler.py`) passes `self.interim_response` through a new recursive `_deep_thaw()` helper (`MappingProxyType` → `dict`, `tuple`/`list` → `list`) before building the agent-mode `RequestSession`, instead of a shallow `dict(...)` copy.
**Why:** `BridgeConfig`'s `_deep_freeze()` (D-023) freezes nested dicts/lists too, so `INTERIM_RESPONSE_JSON` as loaded by the real config path can carry `MappingProxyType`/`tuple` nested inside a top-level dict. A shallow `dict(self.interim_response)` copy left those nested values frozen, and `json.dumps()` on the session payload sent to Voice Live would raise `TypeError: mappingproxy is not JSON serializable` for any agent-mode call whose `INTERIM_RESPONSE_JSON` had a nested object — a connection-breaking bug in every such call, not a cosmetic one. Two independent Opus reviews (code-review and `cso`) converged on this same root cause in round 1 of U07's review. Fixed with a regression test that builds the value via the real `_deep_freeze()` and asserts `json.dumps()` succeeds. The same U07 fix round also added defense-in-depth: `AgentRoute.__post_init__` (`app/routing.py`) now enforces the pinned-version format independently of `bridge_config`'s own check, `_voicelive_connected` is set only after `session.update`/`response.create` succeed, `on_voicelive_ended()` is called under try/except in the receiver's `finally`, and `stop_forwarding_agent_audio()` now drops already-buffered TTS audio, not just future deltas. **Source:** U07 Opus code-review + `cso`, round 1 findings (both independently found the same bug), PR #8.

### D-027 · 2026-09-27 · `CallSession._safe_hang_up()` must not treat a cancelled or transient hang-up attempt as a permanent no-op
Three real defects were found and fixed in the call-ending path (`app/providers/acs/call_session.py`) implementing D-005's single idempotent `request_end()`:
- (#A) A late `on_play_done()` (or a `play_media` failure) could cancel the play-safety timer while its own spawned `_safe_hang_up()` was already awaiting the ACS hang-up HTTP call. `CancelledError` isn't caught by `_safe_hang_up`'s `except Exception`, so the request was silently dropped, and the follow-up retry no-op'd because `_hung_up` was already `True` — the call stayed up with no further attempt to end it. Fixed: timer cancellation now goes through `_cancel_safety_timer()`, which only cancels the timer while it is still merely sleeping (guarded by `not self._hung_up`); the underlying hang-up call is also wrapped in `asyncio.shield()` as defense in depth.
- (#D) `request_end()` can fire before `set_answered()` supplies a `call_connection_id` (e.g. a route-miss `CallConnected` racing ahead of `answer_call()`'s own response). `_safe_hang_up()` used to silently no-op in that case with nothing to ever retry it, leaving the caller connected in silence indefinitely once `wait_timeout` elapsed. Fixed: a new `_hangup_pending_answer` flag records the deferred hang-up, and `set_answered()` finishes it once the connection id is known.
- (#B) Any `HttpResponseError` on hang-up, including a transient 5xx/429, was treated the same as a terminal "call already gone" error, permanently setting `_hung_up` and blocking any future retry. Fixed: only a narrow `{404, 410}` status set is now treated as terminal; anything else clears `_hung_up` so a later call (another end path, or `sweep()`'s new `force_hang_up()`) can retry.
**Why:** this is the unit D-005 and the four design-spec review rounds (D-008) exist to protect — "every way a call ends" must actually end it, not leave the caller connected in silence under a race or a transient failure. Two independent Opus review rounds (code-review + `cso`) confirmed the fixes close the races without introducing a new one, and both reconfirmed `request_end()`'s idempotency, that no double hang-up is possible, that only one Voice Live close task is ever spawned, and that no session is left permanently stuck in the registry (`sweep()` is the backstop either way). A residual, lower-severity gap — transient failures are no longer *permanently* blocked but aren't retried *promptly* either, and the ACS `hang_up()` call itself has no timeout — was logged as Q-010 rather than fixed in this unit, to avoid a third fix-and-re-review cycle on an already twice-reviewed unit. **Source:** U08 Opus code-review, round 1 findings (#A/#B/#D) and round 2 confirmation ("ready to merge"); `cso` round 1 and round 2 both PASS. PR #9.

### D-036 · 2026-09-27 · Corrects D-006: the callback signature is not single-use; `ACS_CALLBACK_JWT_AUDIENCE` should be required, not optional, in deployed environments
**D-006's original text says:** *"The media URL is `/acs/ws/{call_key}/{HMAC("ws:"+key)}` and the callback URL is `/acs/callbacks/{call_key}/{HMAC("cb:"+key)}`. **The "single-use" claim is only true for the websocket signature, not the callback signature.** U12's `cso` review (round 1, finding #6) verified this by reading the actual code and the server's access-log path: the websocket route enforces `ws_used` — the media socket can only be opened once, so a captured `/acs/ws/{call_key}/{sig}` URL is genuinely useless after that single use. The callback route (`/acs/callbacks/{call_key}/{sig}`) has no equivalent single-use guard — it accepts every ACS callback for the call's entire lifetime (`CallConnected`, `PlayCompleted`, `CallDisconnected`, etc.), so the same signed URL remains valid and reusable for as long as the call is active.

**The exposure this creates:** Quart's default access log (`accesslog="-"`, confirmed at `server.py`/`quart/app.py`) writes the full request path — including the signature — to stdout, which lands in Container Apps' Log Analytics. While `ACS_CALLBACK_JWT_AUDIENCE` is unset (today's default, since D-006 made the JWT check optional), anyone with read access to those logs could extract a live call's callback signature and forge a `CallDisconnected` or `PlayCompleted` against that call, tearing it down or interfering with it mid-conversation. This is an insider-only exposure (requires log read access) and is bounded to the life of one call, so `cso` rated it LOW — but it directly contradicts D-006's stated rationale for leaving the JWT check optional, so the rationale itself needs correcting, not just a code fix.

**Correction:**
1. **D-006's "single-use" claim is corrected**, not retracted wholesale: it holds for the websocket signature only. The callback signature is reusable for the call's full duration.
2. **`ACS_CALLBACK_JWT_AUDIENCE` should be required (not optional) in deployed environments.** This was already tracked as Open check 5 / Q-005 ("verify the ACS callback JWT issuer, JWKS URL and audience before enabling `ACS_CALLBACK_JWT_AUDIENCE`... proceed as planned, verify at M6"). Q-005's own scope is extended by this entry: verifying the JWT parameters at M6 is necessary but not sufficient — U15's deploy verification must also confirm `ACS_CALLBACK_JWT_AUDIENCE` is actually set (not merely valid if set) before the deploy is considered complete. Local/dev environments without ACS credentials configured are unaffected; this applies to the real deployed environment only.
3. The HMAC signature itself is not weakened by this finding — it remains a real, cryptographically sound check (`hmac.compare_digest`, purpose-prefixed so a websocket signature can't be replayed as a callback signature or vice versa). The finding is specifically about the *optionality* of the second factor (the JWT check) given that the signature alone is reusable for callbacks, not about the signature's own soundness.

**Why fixed via a decision, not silently in U12's code:** this is a correction to a standing decision's own stated rationale (D-006), not an ordinary bug — the code (U12's PR #20) already implements the JWT check exactly as D-006/the plan specify; what's wrong is D-006's *justification* for making that check optional. Per D-030, the partner has standing authority to resolve tension with this repo's own prior decisions, conditioned on documenting the reasoning in full here — this entry does that. No code change was needed in U12 itself; the fix is a deploy-configuration requirement for U15/M6 and a corrected record for future sessions reading D-006.

**Source:** U12's `cso` security review, round 1, finding #6, PR #20. Partner decision under D-030's delegation (a D-002-adjacent standing-decision correction, the same class of authority D-031/D-032 already used).
